# 05 · 逆向笔记

本文的很多结论不是从官方文档来的（官方基本没有文档），而是**从文件和二进制里读出来的**。

## 一、不需要整包下载：用 HTTP Range 拆 zip

bootstrap 服务器那个 `Nyxian_0.11.5_3.ipa` 有 **112 MB**，而且实测下载速度只有约 63 KB/s
（全下要 30 分钟以上）。但 IPA 就是个 zip，而 **zip 的目录在文件末尾** ——
所以只需要三次请求：

```bash
URL="https://nyxian.app/bootstrap/Nyxian_0.11.5_3.ipa"

# 1) 确认服务器支持 Range，并拿到总长度
curl -sSI "$URL" | grep -iE 'accept-ranges|content-length'

# 2) 取文件尾部，解析出中央目录的位置
LEN=112146995
curl -sS -r "$((LEN-300000))-$((LEN-1))" -o tail.bin "$URL"

# 3) 按中央目录给出的偏移，把整个目录取下来（本例 328146 字节）
curl -sS -r "111818827-112146972" -o cd.bin "$URL"
```

然后解析 `cd.bin` 里的中央目录条目（每条以 `PK\x01\x02` 开头，46 字节固定头 + 变长文件名），
就能拿到全部 1820 个条目的**文件名、压缩后大小、压缩方式、本地头偏移**。

**再按偏移取单个成员**（本地头 30 字节固定 + 文件名 + extra，之后是数据）：

```python
import subprocess, struct, zlib

URL = "https://nyxian.app/bootstrap/Nyxian_0.11.5_3.ipa"

def fetch(a, b):
    return subprocess.run(["curl", "-sS", "-r", f"{a}-{b}", URL],
                          capture_output=True).stdout

def get_member(lho, csize, out):
    """lho = 本地头偏移, csize = 压缩后大小"""
    buf = fetch(lho, lho + csize + 300)
    assert buf[:4] == b"PK\x03\x04"
    nlen, elen = struct.unpack_from("<HH", buf, 26)   # 本地头的文件名/extra 长度
    doff = 30 + nlen + elen
    data = buf[doff:doff + csize]
    method = struct.unpack_from("<H", buf, 8)[0]      # 8 = deflate, 0 = stored
    if method == 8:
        data = zlib.decompress(data, -15)
    open(out, "wb").write(data)
    return data
```

用这个方法，只用几 MB 流量就把需要的主程序、几个 dylib 和 Info.plist 都抽出来了。

## 二、从 Mach-O 里捞字符串

Mach-O 的 `__cstring` 段里躺着大量**界面文案、错误消息、格式模板**，
按二进制里的原始顺序排在一起。按关键词定位然后往前后各取一两千字节，
往往能还原出**一段完整的流程**。

```python
import re
d = open("Nyxian-main", "rb").read()   # Payload/Nyxian.app/Nyxian
i = d.find(b"checking upon nyxian bootstrap")
seg = d[max(0, i-3000): i+7000]
for m in re.finditer(rb"[\x20-\x7e]{4,}", seg):
    print(m.group().decode("ascii"))
```

这一招的效果很不错 —— 比如同时搜 `NXWindowSession` 和 `Switcher`，就把
Nyxian 内部的**窗口服务器架构**整个暴露出来了（见下）。

⚠️ 注意：`__cstring` 里字符串的**排列顺序不等于执行顺序**。别拿字符串相邻当流程相邻。

## 三、`.nxt2c` 文件的格式

`org.emexlabs.rootca.v1.pub.nxt2c`（119 字节）是一个自定义公钥容器。
逐字节拆开是：

```
偏移  长度  内容
0     4     "KP2N"            ← 魔术字
4     4     小端 u32 = 1      ← 版本号
8     4     小端 u32 = 12     ← 名称长度
12    4     小端 u32 = 91     ← 密钥长度
16    12    "org.emexlabs"    ← 名称
28    91    DER 编码的 SubjectPublicKeyInfo
```

那 91 字节再往里剥，是一个标准的 X.509 SPKI：

```
SEQUENCE (0x30 0x59)
  SEQUENCE (0x30 0x13)
    OID 1.2.840.10045.2.1     ← id-ecPublicKey
    OID 1.2.840.10045.3.1.7   ← prime256v1 (P-256)
  BIT STRING (0x03 0x42 0x00)
    04 | X(32) | Y(32)        ← 未压缩的椭圆曲线点
```

**它是一把裸公钥，不是 X.509 证书** —— 没有签发者、没有有效期、没有签名。
它的用途是当**根信任锚**，用来验证 ROM / 包的签名。

还原成标准 PEM 之后可以直接验证：

```bash
openssl pkey -pubin -in org.emexlabs.rootca.v1.pub.pem -text -noout
```

校验值：

```
整文件 SHA-256   47332d1ff5e309e411ee0e54c2ece986d5cf0ea4de1cc0d286c1975add45036c
SPKI   SHA-256   d5c1fed538311d49c4cf08f469cd3f495dd806b550ebd36a19bfede8f73eeff9
```

## 四、bootstrap 的完整顺序

从**内层** App 主程序的 `__cstring` 里读出来的（`checking upon nyxian bootstrap` 附近）：

```
checking upon nyxian bootstrap :3
├ bootstrapping directory structure
├ bootstrapping libraries                    → Shared/lib.zip       （内置）
├ bootstrapping clang include and swift resources
│                                            → Shared/include.zip   （内置）
│                                            → Shared/swift.zip     （内置）
├ bootstrapping rootca folder                ← 下载第一个联网动作
│     https://nyxian.app/bootstrap/org.emexlabs.rootca.v1.pub.nxt2c
│     落到 RootCAs/org.emexlabs.rootca.v1.pub.nxt2c
└ bootstrapping SDK
      https://nyxian.app/bootstrap/iPhoneOS27.0.sdk.zip
done
```

**这里有个关键结论**：前三个阶段用的 `Shared/lib.zip`（64 KB）、`Shared/swift.zip`（17.7 MB）、
`Shared/include.zip`（1.2 MB）**全都打包在 IPA 内部**
（在 zip 里是"未压缩存储"状态，路径 `Payload/Nyxian.app/Shared/*.zip`），
也就是说它们**不联网，只是本地解压**。

→ **所以下载 rootca 是整个 bootstrap 里的第一个联网操作。**
（如果卡在这一步，说明要查的是"联网为什么不行"，而不是"这个文件有什么问题"。）

配套的错误文案是成对出现的，注意区分：

```
downloading "https://.../org.emexlabs.rootca.v1.pub.nxt2c" failed   ← 下载/落盘失败
failed to move emexlabs public rootca key                           ← 下载成功、移动失败
```

外层引导器的 `downloadFile()` 也是同类陷阱：它先 `NSData dataWithContentsOfURL:`，
再 `writeToFile:atomically:`，**返回的却是写盘结果** ——
所以屏幕上写"downloading failed"，实际可能是**写入失败**。

## 五、Recovery 的触发机制

从引导器脚本读出（`JEFI.js` 里的 `scanFor` 逻辑 + `LoaderUI.js` 里作者的注释）。
完整内容见 [02-恢复模式.md](02-恢复模式.md)，这里只记要点：

- 启动时扫描 **1.5 秒**，音量减 = Recovery，音量加 = Verbose Boot
- 扫描器**靠音量变化**感知按键 → 音量在极值时可能扫不到
- Recovery 内：轻点音量上/下移动，**两个音量键同时按住**确认

## 六、内部类名（顺出来的架构）

在内层主程序里搜 `NXWindowSessionTerminal`，会连带掉出一整批类名：

```
NXWindowServer / NXWindowSession / NXWindowSessionApplication
NXWindowSessionTerminal          ← 终端是一种"窗口类型"
NXWindow / NXWindowBar / NXWindowLayerView / NXWindowDelegate
NXAppTile                        ← 切换器里的应用磁贴
NXGuestSceneBridge               ← 把 guest 的画面桥接出来
NXHitSurfaceButton / NXResizeHandle

PELaunchService / PELaunchServiceManager
PEProcess / PEProcessManager / PEUserspaceManager
LDEApplicationWorkspace / LDEApplicationWorkspaceService
appSwitcherView / _windowOrder / _windows / _applications
rebootUserspace                  ← 就是设置里那个 "Userspace Reboot"
```

配合另一批字符串，还能看出项目模板和构建路径：

```
项目类型：Application / Utility / Library / Framework / Kext
语言：    ObjC / Swift / SwiftUI
产物：    $(CACHEROOT)/Payload/$(NXDisplayName).app/$(NXExecutable)
          $(CACHEROOT)/Payload/$(NXBundleIdentifier).kext/$(NXExecutable)
```

**结论**：容器里的东西跑在 **Nyxian 自己的窗口服务器**里，**不会出现在真实桌面上**。

## 七、几条经验

1. **先看版本号再下结论。** 本文写作过程中就因为读了旧版脚本得出了错误结论
   （"Recovery 里没有 Flash ROM"），实测才发现新版有 9 项、旧版只有 6 项。
2. **字符串顺序 ≠ 执行顺序。**
3. **别整包下载。** ZIP 的目录在末尾，Range 请求能省掉 95% 的流量。
4. **留意"报错文案骗人"的情况**：`downloading failed` 可能其实是写入失败。
5. **能实测就别猜。** 这个题材的第三方资料质量普遍不高。
